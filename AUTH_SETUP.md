# Регистрация и хранение пользователей

Главная открывается сразу. Кнопка «Вход» в нижней части боковой панели открывает
регистрацию; «На главную» возвращает назад. После авторизации и выхода
пользователь остаётся на главной.

Экран входа работает без сервера в явно обозначенном деморежиме. Настоящие
пользователи появляются только после подключения проекта Supabase и подтверждения
почты. Демосценарий не создаёт учётных записей.

## Подключение почты

1. Создайте проект Supabase в своём аккаунте. В SQL Editor выполните
   `supabase/migrations/202610080001_profiles.sql` один раз.
2. Скопируйте `.env.example` в `.env.local`. Заполните URL проекта и публичный
   publishable key (либо legacy anon key). Никогда не указывайте `service_role`
   или secret key в переменных `VITE_*`: они доступны браузеру.
3. В Supabase Auth включите Email provider и регистрацию новых пользователей.
   Настройте собственный SMTP для отправки писем реальным пользователям:
   встроенная отправка Supabase ограничена и не предназначена для общего запуска.
4. В Auth URL Configuration задайте Site URL публичного приложения и добавьте
   точный адрес возврата с `/LabS/` в Redirect URLs. Для локальной разработки:
   `http://localhost:5173/LabS/` (при использовании 127.0.0.1 добавьте и его).
5. Перезапустите `npm run dev -- --port 5173 --strictPort`.
   Введите почту, откройте ссылку из письма в этом же браузере и проверьте вход.
   Выход должен вернуть экран регистрации, перезагрузка — восстановить сессию.

Supabase Auth хранит email, подтверждение, идентификаторы провайдеров и сессии.
`public.profiles` хранит UUID, имя и дату создания. Триггер создаёт профиль для
каждой учётной записи; RLS позволяет пользователю читать и изменять только своё
имя. Почта не дублируется в общедоступной таблице. Просмотр всех пользователей
владельцем проекта доступен в Supabase Dashboard → Authentication → Users.
Не добавляйте административный ключ в клиентское приложение.

## Другие способы входа

- Google: создайте OAuth client в Google Cloud, настройте Google provider
  в Supabase с callback URL из панели Supabase. Добавьте URI и разрешённые
  origin в Google Console. Установите `VITE_AUTH_GOOGLE_ENABLED=true` и
  перезапустите Vite. Кнопка использует Supabase OAuth; доступ к письмам не нужен.
- Яндекс: кнопка пока показывает объяснение. Нужны приложение Яндекс OAuth и
  серверная интеграция; обработчик обмена кода и проверки пользователя пока
  не реализован. Не подменяйте её Google OAuth и не храните client secret в Vite.
- Telegram: кнопка пока показывает объяснение. Нужны бот, публичный домен и
  серверный обработчик с проверкой подписи, срока действия и защиты от повторов.
  Telegram не передаёт email. Для объединения с почтовым аккаунтом нужна отдельная
  проверка адреса; нельзя объединять пользователей по неподтверждённым данным.

История разговоров приложения остаётся локальной демонстрацией. Сохранение
разговоров в базе и их изоляция между аккаунтами — отдельная задача. При
подключённой авторизации приложение изолирует локальную историю по UUID.

## GitHub Pages

Публикация настроена в `.github/workflows/deploy-pages.yml`: push в `main`
или ручной запуск Actions → Deploy to GitHub Pages → Run workflow.
В Settings → Pages источником должен быть GitHub Actions. Сборка получает URL
и публичный publishable key Supabase из workflow; `.env.local` в Git не попадает.
Эти значения видны в браузере и не являются административными секретами.

Для этого проекта в Supabase Authentication → URL Configuration задайте
Site URL `https://gokosmos.github.io/LabS/` и добавьте точно такой же адрес
в Redirect URLs. Откройте опубликованный сайт, нажмите «Вход», введите почту и подтвердите вход
по письму. Встроенная отправка Supabase ограничена: для произвольных получателей
настройте собственный SMTP. Если workflow завершился успешно, но регистрация
не работает, проверьте SMTP, redirect allowlist и сетевые запросы Auth.

## Проверки перед запуском

`npm ci` и `npm run build`; затем реальный вход через письмо и настроенный Google.
В двух аккаунтах проверьте, что профиль другого пользователя не доступен через
API, а изменение чужого UUID запрещено RLS. Эта миграция и настоящая доставка
писем требуют проекта Supabase; без него они не проверены на сервере.

## Реферальные ссылки

В «Центре управления» появился раздел «Пригласи друзей». Вошедший пользователь
может скопировать личную ссылку или отправить её через меню «Поделиться».
При переходе сохраняется первый корректный код приглашения в этом браузере;
при регистрации по почте он передаётся в metadata нового аккаунта.

Для постоянного учёта пригласившего примените в Supabase SQL Editor файл
`supabase/migrations/202610090001_referrals.sql` после миграции profiles.
До применения миграции ссылки и передача кода работают, но связь в profiles
не сохраняется. Проверка в базе: зарегистрировать новый аккаунт по приглашению,
подтвердить почту и проверить его `profiles.referrer_id`; обычная регистрация,
несуществующий код и приглашение самого себя не должны назначать пригласившего.
Существующие аккаунты не получают нового пригласившего при повторном входе.
Пользователи не могут менять `referrer_id` через клиентский API.

Начисления, выплаты, число уровней и проценты пока не реализованы. Платёжная
интеграция тоже не подключена; покупка пакетов не начисляет вознаграждения.
